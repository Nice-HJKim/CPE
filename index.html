수업 개요

오늘의 목표는 AWS 서비스를 많이 외우는 것이 아니라, “왜 클라우드를 쓰는가?”를 중심으로 개념 간 관계를 이해하는 것입니다.

클라우드 모델 구분Public / Private / Hybrid, IaaS / PaaS / SaaS
클라우드 가치 이해종량제, 탄력성, 민첩성, 고가용성
설계 원칙 파악느슨한 결합, 복원력, 추적성, Well-Architected
마이그레이션 이해AWS CAF, 7R, 이동·평가 도구
경제성 이해CapEx→OpEx, TCO, Right Sizing, 할인 모델
글로벌 인프라 이해Region, AZ, Edge Location, 글로벌 서비스
수업 흐름 한 문장 “직접 데이터센터를 소유하는 대신 필요한 만큼 빌려 쓰고, 장애에 강하고 확장 가능한 구조로 설계하며, 전 세계 AWS 인프라를 활용한다.”
첫 질문으로 “서버를 직접 사서 운영하는 것과 AWS에서 EC2를 필요할 때 만드는 것의 가장 큰 차이는 무엇일까요?”를 던지면 이후 Pay-as-you-go, CapEx/OpEx, 탄력성까지 자연스럽게 연결할 수 있습니다.

1.1 AWS 클라우드의 이점

클라우드 컴퓨팅의 기본 모델, 서비스 제공 방식, AWS 클라우드의 대표적 이점을 정리합니다.

1) 클라우드 컴퓨팅과 배포 모델

Private Cloud

기업 전용 클라우드

한 기업이 전용으로 구축·운영하는 폐쇄형 클라우드입니다.

Public Cloud

공용 클라우드

인터넷을 통해 여러 고객이 사용하는 클라우드입니다. AWS, Azure, GCP 등이 대표적입니다.

Hybrid Cloud

혼합형

Public Cloud와 Private/온프레미스 환경을 연동하여 함께 사용하는 방식입니다.

시험 포인트
“어디에 구축되어 있는가?”는 배포 모델(Public / Private / Hybrid), “어디까지 누가 관리하는가?”는 서비스 모델(IaaS / PaaS / SaaS)로 구분합니다.

2) IaaS · PaaS · SaaS

모델핵심 의미사용자가 주로 관리서비스 제공자가 주로 관리
IaaS서버 운영에 필요한 IT 인프라 제공OS 위의 애플리케이션, 데이터 등서버, 스토리지, 네트워크, 가상화 기반
PaaS애플리케이션 개발·실행·테스트·관리를 위한 플랫폼 제공애플리케이션과 데이터 중심런타임·미들웨어·OS·인프라
SaaS완성된 소프트웨어 기능을 서비스로 제공서비스 사용애플리케이션을 포함한 대부분
Pay-as-you-go(종량제) 실제 사용한 만큼 비용을 지불하는 방식입니다. 초기 대규모 투자 없이 필요한 만큼 사용하고, 사용량에 맞춰 비용을 지불하는 것이 클라우드 과금의 핵심입니다.

3) AWS 클라우드의 6대 이점

① 고정 비용 → 가변 비용
초기 데이터센터 투자 대신 사용량 기반 비용
② 규모의 경제
대규모 통합 운영으로 더 낮은 단가
③ 용량 추측 불필요
수요에 맞춰 리소스 확장·축소
④ 속도와 민첩성
리소스를 빠르게 확보하고 실험
⑤ 데이터센터 운영 부담 감소
전력·냉각·물리 인프라 운영 부담 이전
⑥ 빠른 글로벌 배포
리전·AZ·엣지 로케이션을 활용

1.2 AWS 클라우드의 설계 원칙

클라우드 환경에서는 한 번에 크게 만드는 것보다, 작은 구성요소를 분리하고 장애를 격리하며 자동으로 복구할 수 있도록 설계하는 것이 중요합니다.

1) 강한 결합 vs 느슨한 결합

Tightly Coupled

강한 결합

구성요소 간 의존성이 크면 하나의 장애가 다른 구성요소로 쉽게 전파될 수 있습니다.

Loosely Coupled

느슨한 결합

구성요소의 상호 의존성을 줄이고 오류를 격리하여 전체 시스템 장애로의 파급을 줄입니다.

2) 모놀리식 vs 마이크로서비스

구분특징수업 포인트
Monolithic기능이 하나의 큰 애플리케이션에 밀접하게 묶여 있음변경·장애의 영향 범위가 커질 수 있음
Microservices작은 서비스 단위로 분리각 서비스를 EC2, Lambda, 컨테이너 등 서로 다른 기술로 구현 가능
추적성 활성화 시스템의 사용자 활동, API 호출, 변경 사항을 기록하고 추적할 수 있어야 합니다. 자료에서는 AWS CloudTrail을 대표 서비스로 제시합니다.

3) 복원력(Resilience)과 자동 장애조치

정상 리소스
→
장애 발생
→
Failover
→
서비스 지속 / 복구

결함이 발생하더라도 정상 리소스로 자동 장애조치하여 시스템이 기능을 지속하거나 빠르게 복구할 수 있도록 설계합니다.

Durability · 내구성

데이터를 잃지 않고 안전하게 보존하는 능력.

Elasticity · 탄력성

수요 변화에 따라 리소스를 자동으로 확장·축소하는 능력.

보안

안정성
자동 복구, 복구 절차 테스트, 수요 대응
성능 효율성
효율적인 컴퓨팅 사용, 수평 확장, 서버리스

낭비 제거, 적정 크기 조정, 관리형 서비스
운영 우수성
작고 잦은 변경, 지속적 개선, 실패에서 학습
지속 가능성
자원·전력 사용 효율화, 활용도 극대화
시험 포인트
문제에서 “자동 복구”, “수요 변화에 따라 확장”, “권한·감사”, “불필요한 비용 제거” 같은 표현이 나오면 각각 안정성, 성능/탄력성, 보안, 비용 최적화와 연결해서 보세요.

1.3 AWS 클라우드 마이그레이션

클라우드 전환은 단순한 서버 이동이 아니라 조직, 기술, 운영, 보안, 재무 관점까지 포함한 변화입니다.

1) AWS Cloud Adoption Framework (AWS CAF)

AWS CAF는 조직의 클라우드 준비 상태를 평가하고 부족한 역량을 식별해 클라우드 전환 로드맵을 수립하도록 돕는 프레임워크입니다.

비즈니스 역량Business
가치·성과, 전략과 클라우드 투자 연결
비즈니스 역량People
조직 변화, 학습, 인재, 변화관리
비즈니스 역량Governance
통제, 감독, 재무/위험 관리
기술 역량Platform
기술 기반과 클라우드 아키텍처
기술 역량Security
보안, 위험, 규정 준수, IAM
기술 역량Operations
안정적 운영, 패치, 구성, 이벤트 관리

2) 클라우드 변환 여정 4단계

1. Envision비즈니스 가치와 기대 결과를 정의
2. Align역량 격차를 파악하고 실행 계획 정렬
3. Launch프로토타입·파일럿을 배포하여 가치 입증
4. Scale비즈니스 가치를 확장하고 지속적으로 개선

3) 마이그레이션 7R 전략

Refactor클라우드 네이티브 기능을 활용하도록 재설계
Replatform기본 구조는 유지하되 일부 핵심 요소를 최적화
Rehost코드 변경 없이 그대로 이동 — Lift and Shift
Repurchase기존 제품을 SaaS 등 다른 상용 제품으로 교체
Relocate하이퍼바이저 수준에서 그대로 AWS로 이동
Retain지금은 이전하지 않고 기존 환경 유지
Retire더 이상 필요 없는 애플리케이션 제거
7R은 ‘이전 전략’이므로 서비스 이름 암기보다 “무엇을 얼마나 변경하는가?”로 비교하면 기억하기 쉽습니다. Rehost는 거의 그대로, Replatform은 일부 최적화, Refactor는 구조 자체를 재설계하는 흐름으로 설명하세요.

1.4 클라우드 경제성

클라우드 비용의 핵심은 초기 대규모 투자를 줄이고, 사용량에 맞춰 지불하며, 지속적으로 사용량을 최적화하는 것입니다.

1) CapEx vs OpEx

CapEx · 자본 지출

미리 구매하고 소유

데이터센터, 서버, 네트워크, 냉각 시설 등을 초기에 큰 비용으로 직접 구매합니다. 최대 수요를 미리 예측하기 때문에 과다 할당 위험도 있습니다.

OpEx · 운용 비용

사용량에 맞춰 운영비로 지불

인프라를 직접 소유하지 않고 사용한 만큼 일상적인 운영비 형태로 지불합니다. 실제 수요에 맞게 비용을 조절하기 쉽습니다.

2) 규모의 경제와 TCO

Economies of Scale

규모의 경제

AWS가 많은 고객의 수요를 통합 운영하면서 서버, 전력, 데이터센터 구축 비용을 더 낮은 단가로 제공할 수 있다는 개념입니다.

TCO

Total Cost of Ownership

서버 구매가격만이 아니라 유지보수, 교체, 시설, 물리 보안 등 모든 직·간접 비용을 함께 비교하는 개념입니다.

Cloud TCO

비용 항목의 이전

시설, 하드웨어 유지·교체, 데이터센터 물리 보안 등의 부담이 AWS 측으로 이동하여 고객의 직접 운영 부담이 줄어듭니다.

3) 클라우드 요금 모델의 3대 축

구분무엇에 따라 비용이 달라지나?
Compute인스턴스 실행 시간 및 CPU/RAM 등 사양
Storage저장 용량과 스토리지 클래스
Data Transfer Out클라우드에서 인터넷/다른 리전 등 외부로 나가는 데이터 전송
자료의 핵심 구분 Inbound(클라우드로 들어오는 데이터)는 무료, Outbound(클라우드에서 인터넷/타 리전으로 나가는 데이터)는 유료로 정리되어 있습니다.

4) 비용 최적화 방법

방법핵심적합한 상황
Right SizingCPU/메모리 사용률 등을 보고 인스턴스 크기 최적화과도한 사양으로 인한 낭비 제거
Reserved Instances / Savings Plans1년 또는 3년 사용 약정으로 할인예측 가능한 장기 사용
Spot InstancesAWS 유휴 용량을 저렴하게 사용하되 중단 가능중단 가능하거나 유연한 워크로드
통합 결제AWS Organizations로 여러 계정의 사용량을 묶어 결제조직 전체 사용량·비용 관리
시험 포인트
“항상 켜져 있고 사용량이 예측 가능”과 “중단되어도 괜찮은 배치 작업”은 서로 다른 구매 옵션을 떠올려야 합니다.

5) 주요 용어 구분

Elasticity · 탄력성

수요에 따라 리소스를 자동으로 늘리고 줄이는 능력.

Availability · 가용성

시스템이 정상적으로 작동하여 서비스를 제공할 수 있는 시간의 비율.

Durability · 내구성

데이터가 손실되지 않고 안전하게 보존되는 능력.

Reliability · 신뢰성

장애 상황에서도 기대한 기능을 수행하는 능력.

Day 1 최종 정리

오늘 배운 내용은 아래 5개의 질문에 답할 수 있으면 큰 흐름을 잡은 것입니다.

5문장으로 정리

  1. 왜 클라우드인가? — 초기 고정 투자를 줄이고 사용량 기반으로 빠르게 확장·축소할 수 있기 때문입니다.
  2. 어떻게 설계하는가? — 느슨한 결합, 추적성, 자동 복구, Well-Architected 원칙을 적용합니다.
  3. 어떻게 이전하는가? — AWS CAF로 조직의 준비 상태를 살피고, 7R 전략과 적절한 이동 도구를 선택합니다.
  4. 어떻게 비용을 관리하는가? — Right Sizing, 약정 할인, Spot, 통합 결제 등으로 지속적으로 최적화합니다.
  5. 어디에서 실행되는가? — Region, AZ, Edge Location을 조합하여 가용성·지연·규제 요구사항을 만족시킵니다.
문제에서 이런 표현이 보이면떠올릴 키워드
“필요한 만큼만 사용”, “초기 투자 최소화”Pay-as-you-go / OpEx
“수요에 따라 자동으로 증가·감소”Elasticity
“장애가 있어도 서비스 지속”High Availability / Resilience / Failover
“API 호출 추적, 누가 변경했는지 확인”AWS CloudTrail
“코드 변경 없이 그대로 이전”Rehost
“DB만 관리형으로 바꾸며 최적화”Replatform
“사용량과 사양을 줄여 낭비 제거”Right Sizing
“고객과 가까운 위치에서 캐싱”Edge Location / CloudFront

종합 확인 문제

수업 마무리 10~15분용. 답은 각 문항을 클릭해서 확인할 수 있습니다.

Q1. 초기 데이터센터 구매 비용을 줄이고 실제 사용량에 맞춰 비용을 지불하는 방식과 가장 가까운 개념은?

정답: OpEx / Pay-as-you-go. 고정적인 선투자 중심의 CapEx를 사용량 기반 운용 비용으로 전환하는 흐름입니다.

Q2. 트래픽 증가에 따라 서버 수를 자동으로 늘리고 감소하면 줄이는 능력은?

정답: 탄력성(Elasticity).

Q3. 한 구성요소의 장애가 전체 시스템으로 퍼지지 않도록 설계하는 원칙은?

정답: 느슨한 결합(Loosely Coupling)과 오류 격리.

Q4. AWS에서 사용자 활동과 API 호출을 기록·추적하는 대표 서비스는?

정답: AWS CloudTrail.

Q5. AWS CAF의 4단계를 순서대로 말해보세요.

정답: Envision → Align → Launch → Scale.

Q6. 애플리케이션 코드를 거의 변경하지 않고 그대로 AWS로 옮기는 7R 전략은?

정답: Rehost (Lift and Shift).

Q7. 기본 아키텍처는 유지하지만 자체 DB를 관리형 DB로 바꾸는 식의 최적화 전략은?

정답: Replatform.

Q8. CPU 사용률이 낮은 대형 인스턴스를 더 작은 크기로 바꾸는 비용 최적화 기법은?

정답: Right Sizing.

Q9. 중단 가능성이 있지만 유휴 AWS 용량을 저렴하게 쓰는 구매 옵션은?

정답: Spot Instances.

Q10. 한 리전 안에서 물리적으로 격리된 데이터센터 집합을 무엇이라고 하나요?

정답: Availability Zone(AZ).

Q11. 전 세계 사용자에게 정적/동적 웹 콘텐츠를 빠르게 전달하기 위한 CDN 서비스는?

정답: Amazon CloudFront.

Q12. 도메인 등록과 DNS 라우팅을 제공하는 AWS 서비스는?

정답: Amazon Route 53.

Q13. AWS 글로벌 네트워크와 Static IP를 이용해 글로벌 애플리케이션 성능과 가용성을 높이는 서비스는?

정답: AWS Global Accelerator.

Q14. 데이터가 손실되지 않고 보존되는 능력과 시스템이 정상 서비스되는 시간의 비율을 각각 무엇이라 하나요?

정답: 내구성(Durability), 가용성(Availability).

Q15. 온프레미스에 AWS 서버/네트워크 장비를 설치해 하이브리드 환경을 구성할 때 떠올릴 서비스는?

정답: AWS Outposts.

마지막 점검 서비스 이름을 외우는 것보다, 문제의 요구사항에서 “비용 / 가용성 / 지연시간 / 운영 부담 / 마이그레이션 변경 수준” 중 무엇을 묻는지 먼저 구분하는 것이 중요합니다.
